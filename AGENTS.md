# AGENTS.md — WP Block Forker

This file is a reference spec, not a pending-task list — the plugin below is
fully built and this describes what was actually shipped, for whoever (human
or Claude Code) is debugging it later.

## What it does

In the block editor, select one or more blocks → block toolbar's "⋮" menu →
"Fork to new post…". A modal asks for a title (pre-filled from the first
selected block's text), a target post type (default `post`, overridable),
and a mode:

- **Copy** — creates a new draft containing the selected blocks. Source post
  untouched.
- **Move** — same, but also removes the selected blocks from the source post.

A second menu item, "Merge into existing post…", writes the selected blocks
into an existing post instead of creating one: the user searches for a target
(any forkable post type, drafts and published alike, the source post excluded),
picks **append** (default) or **prepend**, and copy or move as above. See
"Merging into an existing post".

## Architecture

```
wp-block-forker.php              bootstrap: header, constants, manual requires
includes/
  class-wpbf-fork-service.php    create_fork(), merge_into()
  class-wpbf-rest-controller.php POST wpbf/v1/fork, POST wpbf/v1/merge — used by the editor
  class-wpbf-plugin.php          hook wiring, asset enqueue, forkable-post-types list
  class-wpbf-update-checker.php  embedded GitHub Releases updater (per house convention)
src/
  index.js                       registers the two BlockSettingsMenuControls items, owns which modal is open
  fork-modal.js                  title/post-type/mode form + the fork REST call
  merge-modal.js                 target search/position/mode form + the merge REST call
  shared.js                      token generation, copy/move options, post-success handling
build/                           wp-scripts output — gitignored, generated by `npm run build`
```

**Why `includes/` + manual `require_once`, not `src/` + PSR-4:** this plugin
has a real JS build (`src/` is already claimed by the JS source), so PHP
under `src/` too would collide. Rather than reach for Composer autoloading
just for four classes, the bootstrap file lists them with `require_once` —
zero *runtime* dependencies, one file to look at to see load order. This is
a per-project call, not a change to the scaffold skill's default — see the
Sept 2026 conversation about reconciling `src/` vs `includes/` across the
toolchain generally, which is still open as its own topic.

Composer does now show up in this plugin (see "Building a local
distribution zip" below), but only as a `require-dev` for Phing — a
CI/dev-facing build tool, not something loaded at runtime. That's a
different category from pulling in Composer autoloading for the plugin's
own classes, which is the thing being avoided above.

## Why "move" is handled client-side, not by the REST endpoints

`Fork_Service::create_fork()` and `merge_into()` only ever write to the
*destination*. Neither touches the source post — "move" is handled entirely
client-side instead:
`fork-modal.js` calls `dispatch('core/block-editor').removeBlocks(clientIds)`
after a successful fork. This does **not** immediately persist — it just
updates the editor's local state, and the removal is saved the normal way,
next time the user (or autosave) saves the post. A snackbar tells them
that explicitly. The alternative — the REST endpoint overwriting the
source post's `post_content` directly, in the same request — was
considered and rejected: if the editor has any other unsaved local edits
at fork time, a same-request server-side overwrite of `post_content` races
against whatever the editor itself saves next, and one of the two silently
loses. Going through the editor's own save path avoids that entirely.

If a REST-based "move" is ever needed for some future automation (not the
editor UI), it would need a `Fork_Service` method to overwrite
`post_content` with the remaining blocks, a new REST arg
(`remaining_content`), and a permission check requiring `edit_post`
capability with `context: edit`.

## Idempotency

Every fork request carries a `fork_token`. `create_fork()` checks for an
existing post with that token in `_wpbf_fork_token` postmeta before creating
anything, and returns the existing post ID if found. This covers a retried
REST call after a dropped response (client sees a network error, retries,
but the server had already succeeded) — the standard reason this toolchain
treats creation actions as idempotent.

Provenance postmeta on every forked post: `_wpbf_source_post_id`,
`_wpbf_fork_mode`, `_wpbf_fork_token`.

## Merging into an existing post

`Fork_Service::merge_into()` (`POST wpbf/v1/merge`) concatenates the
selected blocks' serialized markup onto the target's `post_content` —
`existing + "\n\n" + new` for append, reversed for prepend. No block parsing;
it's plain string concatenation, which is why only start/end positions exist
(see "Not included").

- **Idempotency** is per *target*, not per fork: a target can receive many
  merges, so `_wpbf_merge_token` is a non-unique postmeta, one row per merge.
  A replayed `merge_token` returns success without writing again. The replay
  check runs before the lock check, so a retry of a request that already
  succeeded isn't turned into a 409 by someone opening the post in between.
  Two *concurrent* identical requests can still both write — same accepted
  limitation as fork. If `add_post_meta()` fails after the content write, it's
  logged and success is still returned: reporting failure would invite a retry
  and a duplicate append.
- **Slashing:** `wp_update_post()` expects slashed input and unslashes it;
  REST params arrive unslashed. The content goes through `wp_slash()` first,
  otherwise backslashes inside block comment JSON (`\u003c`, `\"`) are eaten
  and the block's attributes no longer parse.
- **Why overwriting the target server-side is fine here** when overwriting the
  *source* was rejected (above): the source is the post open in the editor
  making the request, so a server-side write races that editor's own next
  save. The target is never the post making the request — `source == target`
  is rejected with 400 — and `wp_check_post_lock()` returns 409 if *another*
  user has it open in an editor. The same user with the target open in a
  second tab is **not** protected (core treats your own lock as no lock); that
  tab's next save will overwrite the merge. `wp_update_post()` writes a
  revision, so the pre-merge content is recoverable.
- Rejected targets: trashed or auto-draft posts (404), post types that aren't
  public + `show_in_rest` (400).
- `mode` is not sent to or stored by the merge endpoint (unlike fork, where it
  is provenance on the new post) — the target is an existing post that can
  have many merges, and the revision is the audit trail.

## Capability model

`current_user_can( 'edit_post', $source_post_id )` (object-specific, so an
author can't fork out of someone else's post) AND
`current_user_can( $target_post_type->cap->create_posts )`.

Merge: `edit_post` on the source AND `edit_post` on the target, both
object-specific. No `create_posts` check — nothing is created. Nonce is
handled automatically by `@wordpress/api-fetch`'s default middleware — no
manual nonce plumbing needed since the editor already wires this up.

Multi-selecting across different nesting levels isn't handled specially —
`getBlocksByClientId()` + `serialize()` just takes whatever's selected at
face value. Fine for the common case (selecting sibling blocks); an edge
case worth knowing about if someone reports a fork producing unexpected
nesting.

## One thing to verify before relying on this in production

`BlockSettingsMenuControls`'s render-prop signature — destructuring
`{ selectedClientIds, onClose }` in `src/index.js` — is used from memory,
not verified against the installed Gutenberg version's source. `npm run
build` confirms the imports resolve to real `@wordpress/*` packages and the
JS compiles cleanly, but that doesn't confirm the render-prop *shape* is
still `{ selectedClientIds, onClose }` on whatever WordPress version this
installs on. First thing to check if the menu item doesn't appear, or
`selectedClientIds` comes back `undefined`.

## Not included

- No settings screen — nothing here is configurable, so there's nothing to
  put on one.
- No handling for reusable/synced blocks beyond what `serialize()` /
  `wp_insert_post()` already do natively (a synced block reference forks as
  a reference, not a copy of its content — this is probably the right
  default, but untested).
- No `uninstall.php`. The only data this plugin owns is the `_wpbf_*`
  postmeta on forked posts (provenance, not anything sensitive) — leaving it
  behind on uninstall is harmless, and it's on the *forked posts themselves*
  which the user owns regardless of whether the plugin is still active.
- No REST support for creating a fork of a fork's *ancestor chain* — a
  forked post doesn't currently expose its `_wpbf_source_post_id` in the UI
  anywhere. Would need an admin column or a REST field if that's ever wanted.
- No WP-CLI command (`wp block-fork`, `CLI_Command`, `Fork_Service::update_source_content()`,
  `Fork_Service::derive_title()` were removed 2026-09-04). This plugin is
  editor-only by design: the CLI path duplicated block-selection logic
  (index-based instead of clientId-based), and deliberately ran with no
  capability checks (shell access treated as trusted) — real attack surface
  and maintenance cost for a headless use case nobody had asked for. If a
  real automation need for headless forking shows up later, re-add it as its
  own scoped feature rather than resurrecting this version wholesale.

- No insertion-point picker for merge (e.g. "after this heading") — it would
  need `parse_blocks()` on the target, an outline UI in the modal, and a plan
  for the target changing between pick and submit. Append/prepend covers the
  motivating case (a fragment too thin to stand alone folded into a bigger
  post) at a fraction of the surface area; re-add as its own feature if
  someone actually needs it.
- No extra confirmation when merging into a *published* post. Gate is
  `edit_post` on the target, the modal shows the target's status, and the
  revision makes it recoverable — a confirm step would add friction to the
  main use case (folding into an existing live article).

## Building a local distribution zip

`composer install && vendor/bin/phing dist` builds a zip identical in shape
to what a real release produces, without pushing a tag. Steps, per
`build.xml`:

1. `npm ci && npm run build` (same as building for local dev use).
2. Copy the repo into `build-dist/wp-block-forker/`, excluding dev-only
   files (`node_modules/`, `vendor/`, `src/`, `bin/`, `build.xml`,
   `composer.*`, `package*.json`, docs, VCS dirs — see `build.xml`'s
   `<exclude>` list, kept in sync with `.distignore`).
3. `bin/build.sh` stamps `{{VERSION}}` in the copied `wp-block-forker.php`
   with `<latest git tag>-<short commit hash>` (e.g. `0.1.0-c80a825`) —
   distinct from a real release's clean `X.Y.Z`, so a locally built zip is
   never mistaken for one from GitHub Releases.
4. `bin/package.php` zips `build-dist/wp-block-forker/` into
   `build-dist/wp-block-forker.zip`, honoring `.distignore`.

This exists to let you inspect exactly what a release zip will contain
before tagging one — `build-dist/` is gitignored, throwaway output.

**This does not replace `.github/workflows/release.yml`.** The two paths
solve different problems and currently duplicate some logic rather than
share it: CI does its own version-stamp (from the pushed tag) and its own
`rsync` + `zip` (not `bin/package.php`), and never calls `build.xml` or
Phing at all. If they ever drift in what they include/exclude, `.distignore`
is the CI side's source of truth; `build.xml`'s `<exclude>` list needs
updating to match by hand.

## Versioning and releases

**Scheme: semver, tags `vX.Y.Z`, `0.x` until the author calls it stable.**
While `0.x`: a minor bump is a new feature or a breaking change, a patch bump
is a fix only. There are no criteria set yet for 1.0.0; the REST contract is
namespaced `wpbf/v1`, so a breaking change to it after 1.0 should be a new
namespace rather than a silent edit. The first release is intended to be
`v0.2.0` (merge is a new capability; the fork backslash fix rides along).
Pre-releases use a pre-release tag (`v0.3.0-rc.1`) **and** GitHub's
"pre-release" checkbox: the updater reads `/releases/latest`, which GitHub
defines as the newest non-draft, non-pre-release, so ticking it keeps an RC
away from every installed copy.

**The git tag is the only source of truth.** Nothing in the repo holds the
version number:
- `wp-block-forker.php` carries `{{VERSION}}` placeholders (header and
  `WPBF_VERSION`), stamped at build time — from the pushed tag in CI, from
  `<latest tag>-<short hash>` in a local `phing dist`.
- `package.json`'s `"version": "0.1.0"` is a placeholder npm requires nothing
  of; it is not read by the build, the plugin, or CI, and is deliberately not
  kept in sync. Don't bump it.
- There is no `CHANGELOG.md`. The changelog is the GitHub Release body
  (`Update_Checker::plugins_api()` shows it in the "View details" modal), so
  there is one place to write it and nothing to drift. Use "Generate release
  notes" and edit.

**Cutting a release:** `main` clean and pushed, then
`git tag vX.Y.Z && git push --tags`. `.github/workflows/release.yml` runs
`npm ci && npm run build`, stamps `{{VERSION}}` from the tag with the `v`
stripped, and attaches `wp-block-forker.zip` to the GitHub release. The
embedded `Update_Checker` in `includes/class-wpbf-update-checker.php` points
at `jesgs-interactive/wp-block-forker` — update that constant if the repo ever
moves. Check the workflow run and the attached asset's name
(`wp-block-forker.zip` — the updater matches on it) before telling anyone to
update. The workflow also triggers on `release: published`, so creating a
release through the GitHub UI (which creates the tag) can fire it twice; the
second run just re-uploads the same asset.

### Update checker and non-release versions

`Update_Checker::check_update()` offers an update whenever
`version_compare( latest_tag, WPBF_VERSION, '>' )`. Two things about that,
checked with `version_compare()` on this ddev site (WP_DEBUG is `true` here via
`.ddev/config.yaml`):

- **An unstamped source checkout is treated as older than every release.**
  The checker skips versions containing `{{`, but only `&& ! WP_DEBUG`, so on
  a WP_DEBUG site that guard is off and `{{VERSION}}` compares lower than
  `0.2.0`. Once a release exists, the dev site is offered an "update" on the
  source checkout. Accepting it would run core's plugin upgrader, which
  replaces the plugin's directory — here, the git working copy. (That last
  step is from how core's `Plugin_Upgrader` behaves, not something tested
  here.) Don't click update on a source checkout.
- **Locally stamped builds compare inconsistently.** `0.2.0-abc1234` is
  older than the real `0.2.0` (the letters read as a pre-release suffix), but
  `0.2.0-1234567` or `0.2.0-1ab2c34` is *newer* — a hash that starts with
  digits reads as an extra patch segment. So whether a local build is offered
  the release depends on what its commit hash looks like.

Neither affects installs from a release zip, which carry a clean `X.Y.Z`.
